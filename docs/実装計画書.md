# アンペア消費可視化アプリ 実装計画書

## 1. 目的

「[要件定義書](./要件定義書.md)」および「[設計書](./設計書.md)」に基づき、初期リリースを検証可能な単位に分けて実装する。各ステップのチェック欄と進捗欄を更新し、実装・テスト・受け入れ確認の状況を追跡する。

## 2. 進捗サマリー

### 状況の記入ルール

- 各ステップのチェック欄を、着手時に `[ ]` から `[/]`、完了時に `[x]` へ更新する。
- ステップ完了後に本表の全体状況、完了数、最終更新日、現在のステップを更新する。
- 仕様変更や判断待ちが生じた場合は、該当ステップの備考と「判断・変更履歴」に記録する。
- ステップ完了は、記載した成果物と完了条件を満たし、必要な検証を実施した時点とする。

## 3. 実装ステップ

### ステップ1: 既存構成の確認と土台の整理

**目的:** 既存のNext.js画面・共通UI・テスト配置を把握し、アンペア画面への置き換え準備をする。

- [ ] 現行のホーム画面、共通レイアウト、ヘッダー、ダークモード、スタイル、テスト構成を確認する。
- [ ] 実装ファイルとテストファイルの配置を既存規約に合わせて確定する。
- [ ] SQLiteメッセージ機能、API、型、テスト、README記述の参照箇所を洗い出す。
- [ ] アンペア画面実装後に不要となるSQLite関連コード・依存関係の削除範囲を確認する。

**成果物:** 確定したファイル配置と削除対象。既存の共通ヘッダーおよびテーマ機能を維持する方針。

**完了条件:** 実装対象と既存機能への影響が明確で、不要コードの削除が他の利用箇所に影響しないことを確認している。

**備考:** 設計書のファイル配置案と現行構成が異なる場合は、現行のテスト・命名規則に合わせる。

### ステップ2: 型・入力検証・集計ロジック

**目的:** UIに依存しないドメイン処理を先に実装し、整数の0.1A単位で一貫して計算する。

- [ ] 家電、画面状態、計算結果のTypeScript型を定義する。
- [ ] 10進文字列を0.1A単位の整数に変換し、指数表記・負数・非有限値・刻み不正などを拒否する。
- [ ] 上限値（0.1A〜60.0A）と家電値（0A以上）の検証を実装する。
- [ ] 有効状態・起動中状態・起動時値の有無に従った集計、残り／超過量、上限状態を実装する。
- [ ] 現在値順の上位10件と「その他」の区分生成を実装する。同値時は家電名、ID順とする。
- [ ] 境界値、同名家電、起動時値未登録、区分合計一致を含む単体テストを追加する。

**成果物:** ドメイン型、検証・計算関数、対応する単体テスト。

**完了条件:** 合計・残り・超過量が整数演算で求められ、無効家電除外や起動時値の代用を含む単体テストが通る。

### ステップ3: CSVカタログと全件検証

**目的:** CSVを初期カタログとして安全に読み込み、不正データがある場合に部分表示を防ぐ。

- [ ] `public/data/appliances.csv` を作成し、要件定義書の12種類・参考値・注記・初期無効状態を反映する。
- [ ] BOM、LF/CRLF、引用符・カンマ・改行を扱うCSVパーサーを実装する。
- [ ] ヘッダー、列数、家電名、アンペア値、初期有効状態、50台上限を全行検証する。
- [ ] 行番号と原因が分かるエラー情報を返し、1行でも不正ならカタログ全体を失敗させる。
- [ ] 正常系、CSV構文、ヘッダー、列数、値不正、全件失敗の単体テストを追加する。

**成果物:** 初期CSV、CSV解析・検証処理、単体テスト。

**完了条件:** カタログの12件が所定の値で読み込め、無効な行を黙って除外せず、失敗原因を特定できる。

### ステップ4: ダッシュボードのロード状態と初期表示

**目的:** CSVロード中・成功・失敗の状態を明示し、成功時だけ集計画面を表示する。

- [ ] ホーム画面をアンペア状況画面の入口に置き換える。
- [ ] CSV取得、HTTPエラー処理、全件検証、再試行操作を実装する。
- [ ] 判別可能なロード／エラー／準備完了状態を管理し、エラー時は一覧・合計・グラフを表示しない。
- [ ] 成功時は上限20.0A、CSV由来の有効状態、起動中OFFで初期化する。
- [ ] 初期表示、ロード、CSVエラー、再試行のコンポーネントテストを追加する。

**成果物:** ダッシュボードの状態管理とCSVロード表示。

**完了条件:** CSVエラー時に合計を誤表示せず、再試行で正常な初期状態へ移行できる。

### ステップ5: 上限設定と家電の操作

**目的:** 利用者が有効な家電と上限を操作し、その場で確定状態を更新できるようにする。

- [ ] 上限値の入力・適用・エラー表示を実装し、無効入力中も最後の確定値を維持する。
- [ ] 家電の追加・編集・削除フォームを実装する。名前重複は許可し、編集ではIDと状態を維持する。
- [ ] 家電追加時は有効ON、起動中OFFとする。
- [ ] 登録50台上限、100V対象の案内、入力欄に関連付くエラーを実装する。
- [ ] 一覧から有効／無効および起動中／通常運転中を独立して切り替えられるようにする。
- [ ] 合計計算の更新、境界値、50台上限、同名レコード、状態の独立性をテストする。

**成果物:** 上限設定、家電フォーム・一覧操作、関連コンポーネントテスト。

**完了条件:** 有効な操作だけが画面状態に反映され、変更時に集計対象が正しく更新される。

### ステップ6: 数値サマリー・グラフ・アクセシビリティ

**目的:** 上限との関係をグラフとテキストの両方で理解できる画面にする。

- [ ] 合計、上限、残り／超過量、上限内／到達／超過の状態表示を実装する。
- [ ] 上位10家電と「その他」の積み上げ横棒、凡例、アンペア値、上限マーカー、目盛りを実装する。
- [ ] 超過時の画面内バナー、家電0件時の案内、起動時値未登録時の説明を実装する。
- [ ] 100V基準・個別回路対象外・遮断保証なし、およびリロード時に初期化される説明を常時表示する。
- [ ] 読み上げ用説明、ラベル、フォーカス、エラー関連付け、色以外の状態表現を実装する。
- [ ] 狭い画面で主要数値・操作・凡例を確認できることを確認し、表示とアクセシビリティのテストを追加する。

**成果物:** サマリー、グラフ、状態案内、レスポンシブ・アクセシビリティ対応。

**完了条件:** 棒区分の合計が数値合計と一致し、上限との位置関係が矛盾せず、同じ情報をテキストでも確認できる。

### ステップ7: 既存デモの整理と関連ドキュメント更新

**目的:** 新しいアプリの内容と矛盾するデモ機能・説明を整理する。

- [ ] SQLiteメッセージ機能のコード、API、型、専用テストを削除する。
- [ ] 利用箇所がないことを確認したうえでSQLite関連依存を削除し、ロックファイルを更新する。
- [ ] ホーム画面テストをアンペア画面の動作に置き換える。
- [ ] READMEの概要、機能、構成、API・DB説明、テスト案内を実装後の内容に更新する。
- [ ] アプリ名・メタデータを必要に応じて更新する。

**成果物:** 不要なデモ機能を除いたコードベースと、現状に一致するREADME。

**完了条件:** SQLiteデモへの不要な参照が残らず、ヘッダー・ダークモードなど維持対象の既存機能が動作する。

### ステップ8: 総合検証と受け入れ確認

**目的:** 要件定義書の受け入れ条件を実装結果に照らして確認する。

- [ ] 上限20A初期値、最大60A、0.1A刻み、リロード初期化を確認する。
- [ ] 有効／起動中状態、起動時値未登録、同名複数台、50台上限を確認する。
- [ ] CSV失敗時の全体エラーと、合計・グラフを表示しない動作を確認する。
- [ ] 上限内・到達・超過、上位10件・その他、グラフと数値の整合を確認する。
- [ ] 画面幅、キーボード操作、スクリーンリーダー向けのラベルと代替情報を確認する。
- [ ] `npm test -- --runInBand`、`npm run lint`、`npm run build` を実行し、結果を記録する。
- [ ] `git diff --check` と変更差分を確認し、未対応項目や既知の制約を記録する。

**成果物:** 受け入れ確認結果、テスト・lint・buildの実行結果。

**完了条件:** 要件定義書の受け入れ条件を満たし、必須検証が成功している。未達があれば該当ステップへ戻り、修正後に再確認する。

## 4. 依存関係と並行作業

基本順序は **1 → 2 → 3 → 4 → 5 → 6 → 7 → 8** とする。ステップ2の型・検証・集計設計をステップ3のCSV検証で再利用する。ステップ4はステップ3完了後、ステップ5はステップ2・4完了後、ステップ6はステップ2・4・5完了後に着手する。ステップ7のREADME更新・不要機能整理は、削除対象の確定後に実施し、ステップ8で全体を検証する。独立して作業できる場合でも、同じ画面や設定ファイルを同時編集しない。
